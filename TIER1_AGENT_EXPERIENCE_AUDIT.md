# Tier 1 Agent Experience Audit

**Audit basis:** current checked-out source, tool registry, public API, P0?P4 modules, workflow docs and tests. This report was written before implementation changes.

## Findings

- P0?P4 engines already exist and should be reused: repository/UI analysis, knowledge routing, ModificationPlanner, controlled edit gate/ledger, verification engine and runtime critic.
- `orchestrate_ui` is an intent/policy router in `uiux/engine/orchestrator.py`; it is not a task lifecycle controller and does not invoke P0?P4. Refactor its decision logic into/reuse a shared orchestration core; do not add a parallel orchestrator.
- There is no general TaskSession/artifact store. Runtime screenshots and reports already use `<project>/.evidence/<session>`; reuse that evidence root for task session metadata and canonical artifact files, rather than introducing another root/store.
- The handoff is currently caller-managed: profile ? knowledge plan ? modification plan ? P3 edits/ledger ? P4 session/evidence are passed as JSON by the consumer.
- P3 is a scope checker and ledger builder, not a source editor. `ChunkExecutor.execute_plan()` explicitly says edits are applied by the host agent; end-to-end orchestration must make this boundary explicit and provide a resumable DO handoff.
- P4 surfaces overlap: `verify_implementation` uses `VerificationEngine`, while `run_runtime_validation` uses the runtime critic/repair loop. Reuse both as existing verification routes; do not replace either.
- Existing `self_test` checks package health; runtime capability detection is in `detect_runtime`/capability functions. A user-facing doctor can compose/reuse those checks.
- Input validation currently returns the established error envelope. It does not provide field-specific example/next_action fields required for ergonomic schema failures. Public schema linter is not enforcing descriptive nested object shapes.

## Required subsystem mapping

| P0?P4 | Existing implementation | Required reuse / boundary | Current gap |
|---|---|---|---|
| P0 SEE | `analyze_repository`, `analyze_existing_ui`, `map_ui_structure`, UI state detector, preservation profile builder | Invoke existing analysis once and retain profiles plus affected surfaces/baseline references in task artifact | No shared task state; caller retains outputs; insufficient-context results are not translated to task-level `NEEDS_INPUT` |
| P1 KNOW | `route_knowledge`, `build_knowledge_plan`, knowledge router/catalog, recipes | Pass P0 profile internally to existing router/planner and persist knowledge plan/ref | Separate calls currently require consumer to manually carry router inputs and output |
| P2 THINK | `ModificationPlanner.plan()`, plan validators/permission gate, validation handoff | Pass P0/P1 artifacts and permission response into current planner; retain all plan outputs | Consumer constructs multiple arguments; permission does not stop a unified pipeline because none exists |
| P3 DO | `check_execution_gate`, `guard_edits`, `ChunkExecutor`, scope lock/change ledger/deviation | Reuse gates and ledger; route `PlanDeviation` back to THINK | P3 consumes caller-created edits and does not modify files; no task controller stores report/deviation |
| P4 CHECK | `VerificationEngine`, `verify_implementation`, runtime critic, evidence/runtime tools, repair planner | Reuse verification/evidence and map root cause to required phase | Caller assembles session manually; critic and verifier paths are separate; root-cause repair routing is not centralized |

## Interface and storage audit

- **Tool registry:** `uiux/core/tools.json` defines 31 tools; MCP derives public tools from it. `uiux.api.call_tool()` validates against schemas then dispatches through `_DISPATCH`. No `run_ui_task` or `doctor` exists at audit time.
- **CLI:** `uiux.cli` has `version`, `tools`, `architecture`, and `call`; no `doctor` command. Compatibility scripts remain wrappers around the API.
- **MCP:** stdio lifecycle and errors are implemented in `adapters/mcp`; adding registry entries is sufficient for discovery, but tool behavior/schema must fit existing transport.
- **P0:** public API `analyze_repository`, `analyze_existing_ui`, `map_ui_structure`; `preservation.py` and `ui_state.py`; all are deterministic/read-only scans.
- **P1:** public API router and knowledge-plan entrypoints delegate to `engine/knowledge_router`; knowledge registries/catalog exist.
- **P2:** `ModificationPlanner.plan()` returns rich plan with planning gate, permission state and verification contract. Permission analysis is available through existing plan status/permissions APIs.
- **P3:** execution gate and `guard_edits` use `ModificationPlanner`/`ControlledEditingEngine`; the host agent remains the actual source editor. The current `guard_edits` schema needs verification against `apply_edit` signature and ledger behavior.
- **P4:** `verify_implementation` calls the verification engine; runtime critic and repair helpers are separately registered. Runtime evidence uses `<project>/.evidence/<session>` with manifests. This is the only existing filesystem-backed session-like storage; it is evidence storage, not a task store today.
- **State/errors:** no canonical `TaskSession` or cross-call task state. Public exceptions are centralized in `core/errors.json`; `call_tool` converts failures to established structured error envelopes, but task-level recoverable statuses/next actions do not exist.
- **Public schemas:** arbitrary nested objects are common and are not enough for agent usability; schema checker supports only a JSON Schema subset and currently validates tool shape, not complete semantic documentation. `guard_edits.edits` requires focused audit against editor fields before changing it.
- **Tests:** phase tests exist for P0, P1, P2, P3, P4 and integration/registry/CLI/MCP compatibility. No single `run_ui_task` acceptance flow, repair-routing integration, projection-size test, or doctor tests exist.

## Scope decisions mandated by the specification

- Reuse the existing `orchestrator.py` policy/routing logic and current P0?P4 engines; expose one sequential task API and keep `orchestrate_ui` as a compatibility wrapper over shared orchestration decisions.
- Persist task state and phase artifacts under the existing target-project `.evidence` session root; do not add another artifact store.
- Add only the specified agent workflow, projections, actionable recoverable statuses, and capability doctor. Keep existing P0?P4 algorithms, runtime architecture, design knowledge and business rules intact.
- P3 cannot execute source edits itself by current contract. `run_ui_task` must not imply it edited the project: DO is a guarded handoff/ledger phase driven by explicit edits, with truthful `PARTIAL`/`NEEDS_INPUT` when the host has not supplied/applied them.

## Compatibility baseline

- Public tool IDs and old input defaults remain compatible; new `verbosity` inputs are additive and default to legacy `full`.
- `orchestrate_ui` result shape and legacy routing decision must remain available while its implementation calls the shared core.
- MCP/CLI adapters consume the central tool registry/API and should not need separate workflow logic.
- The specification?s full end-to-end claim depends on an agent applying real code edits between DO and CHECK; this cannot be represented as an automatic filesystem edit by P3 without violating the existing P3 contract. The unified tool can own plans, references, gates and routes, while reporting this boundary accurately.
